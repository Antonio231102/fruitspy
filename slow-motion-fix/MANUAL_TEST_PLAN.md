# Manual physical-device validation

These steps require manual execution on a physical device. Record the exact generated manifest because the endpoint and per-user signing identity make each installable APK environment-specific.

## Test artifacts

Baseline:

```text
User-supplied original Fruit Ninja 1.7.6 APK
SHA-256 5e94d16234504f5d2b6948b59371d8535c4364249b76e2533bba09114c808650
```

Candidate:

```text
APK generated by python patcher/patch_apk.py
SHA-256 recorded in the adjacent .apk.manifest.json
```

Both APKs use package `com.halfbrick.fruitninja`, but the original and locally generated APK normally have different signing certificates. Back up saves before changing installations. APKs generated later with the same persistent local FruitSpy key can update one another.

## Record the environment

Before each run, record:

- Device model and SoC
- Android version/API level
- Display refresh-rate setting
- Battery/performance mode
- Whether the device is charging
- Whether automatic date and time is enabled
- APK SHA-256 under test

Keep the display refresh rate and power settings unchanged between baseline and candidate measurements.

## Baseline measurement

1. Install the baseline APK if it is not already installed.
2. Fully stop and reopen the app.
3. Start a mode with a visible fixed-duration countdown, preferably a 60-second round.
4. Measure real elapsed time from the first visible `60` to the round ending at `0`. Recording the screen and checking timestamps afterward is more precise than a handheld stopwatch.
5. Repeat twice.
6. Note whether fruit movement, menu animation, particles, and sound appear uniformly slowed or merely stuttery.

A simulation-clock defect should make the in-game countdown and motion advance more slowly than real time. GPU jank alone should drop frames without proportionally extending the game timer.

## Install the candidate

An update installation works when the installed APK and candidate use the same persistent local FruitSpy signing key:

```powershell
adb install -r "PATH_TO_PATCHED_APK"
```

Android 14 or newer may require:

```powershell
adb install --bypass-low-target-sdk-block -r "PATH_TO_PATCHED_APK"
```

If the device has the original application or a build signed by another key, preserve its data before uninstalling it. Android rejects an update whose signing identity differs.

## Primary acceptance test

1. Fully stop and reopen the patched app.
2. Repeat the same fixed-duration round twice under the same device settings.
3. Compare real elapsed duration against baseline.
4. Observe fruit trajectories, countdown speed, particles, UI animation, and audio synchronization.

Primary pass criteria:

- A nominal 60-second round lasts 57–63 real seconds.
- Fruit and UI motion no longer appear uniformly slow.
- Audio remains synchronized.
- No new crash, freeze, or severe stutter occurs.

Strong confirmation of the diagnosis is a baseline duration materially over 63 seconds followed by a patched duration within 57–63 seconds.

## Lifecycle safety tests

The hardened candidate uses a monotonic clock and replaces frame gaps above 250 ms with one normal 16.667 ms frame. Verify the guard behavior:

1. Start a round, background the app for 30 seconds, and resume it.
2. Repeat by locking the screen for 30 seconds and unlocking it.
3. Rotate or trigger another activity only if normal device/game use permits it.
4. Confirm the next frame does not jump physics forward, instantly end the round, eject all fruit, corrupt audio, freeze, or crash.
5. Return to the menu and start another round.

Any large one-frame jump indicates that the injected guard did not execute as designed. A freeze or crash may indicate an ABI-specific syscall or injected-code defect.

## Display and load tests

Where the device supports them:

1. Repeat once at 60 Hz.
2. Repeat once at the highest available refresh rate.
3. Repeat with normal battery mode; avoid comparing a power-saving baseline against a performance-mode candidate.
4. Play a visually busy mode and distinguish uniform slow motion from intermittent dropped frames.

Correct elapsed-time simulation should preserve game speed even when rendering misses frames.

## Online test

After offline timing passes:

1. Install the candidate on both players when practical.
2. Test each player as host.
3. Complete at least one full online round.
4. Confirm both clients' countdowns and fruit motion remain synchronized.
5. Leave the room connected beyond six minutes, then continue manually.

A mixed patched/unpatched match is useful diagnostically but is not the preferred final configuration because the two clients may advance simulations at different rates.

## Long-session test

Before calling the patch production-ready:

- Leave the app foregrounded for more than 72 minutes, then start or continue play to cross the low 32-bit microsecond wrap interval.
- Confirm countdown, motion, and audio remain continuous across the boundary.
- System wall-clock changes are not a required test for the hardened candidate because `CLOCK_MONOTONIC` is independent of civil time.

## Failure evidence

If a test fails, preserve:

- Exact APK SHA-256
- Device/API/refresh-rate details
- Real duration versus in-game duration
- Whether failure followed launch, background/resume, screen lock, or online connection
- A screen recording when possible
- Relevant `adb logcat` output from the run

Do not modify the APK between a failed run and collecting its hash.
